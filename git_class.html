0) Comprendre Git vs GitHub

Git = le moteur de versioning (sur ton ordinateur). GitHub = la plateforme (hébergement + collaboration).

Définition

Git (local)

Git enregistre l’historique d’un projet sous forme de commits. Tu peux revenir en arrière, créer des branches, comparer des versions, fusionner des travaux.

  • Travail local : dossier de ton projet + répertoire .git
  • États : fichiers modifiés, index (staging), commits
  • Branches : pointeurs vers des commits
Définition

GitHub (distant)

GitHub héberge des dépôts Git “sur internet” et ajoute des outils : issues, pull requests, revue de code, actions (CI/CD), permissions, pages web…

  • Collaboration : PR, reviews, discussions
  • Automatisation : GitHub Actions
  • Publication : Releases, GitHub Pages

1) Comment fonctionne un dépôt GitHub

Savoir lire un dépôt : branches, README, commits, tags, releases, PR, issues.

Structure

Anatomie d’un dépôt

  • Code : fichiers + dossiers du projet
  • README.md : page d’accueil du dépôt (quoi / installation / usage)
  • .gitignore : fichiers à ne jamais versionner (cache, outputs, secrets)
  • LICENSE : conditions de réutilisation
  • Branches : main + branches de features/fix
  • Tags / Releases : versions publiées (v1.0.0…)
README

README : le minimum

Un bon README répond en 30 secondes : “C’est quoi ? Comment j’installe ? Comment j’utilise ?”

Template README.md 
# Nom du projet

## Objectif
Une phrase claire sur le but du projet.

## Installation
```bash
pip install -r requirements.txt
```

## Utilisation
```bash
python main.py --input data.txt
```

## Structure du dépôt
- `data/` : données brutes
- `src/` : code source
- `notebooks/` : notebooks Jupyter

## Licence
Ce projet est sous licence MIT.
Collaboration

Issues & Pull Requests

Issue = ticket (bug, idée, tâche). PR = proposition de modification vers une branche cible (souvent main), avec discussion/review puis fusion.

  • Workflow standard : Issue → branche → commits → PR → review → merge
  • Avantage : historique propre + discussion centralisée

Vocabulaire

Remote, origin, upstream

Un remote = une URL nommée vers un dépôt distant. Par convention :

  • origin : le remote principal (souvent ton dépôt GitHub)
  • upstream : le dépôt source si tu as “forké” un projet
Lecture

Lire ce qu’il se passe entre remote et local

Commandes “diagnostic” 
# Où suis-je ?

          git status

          # Quels remotes sont configurés ?
          git remote -v

          # Quelles branches existent localement et à distance ?
          git branch -a

          # Quelles branches distantes sont connues localement ?
          git branch -r

          # Tout l'historique des commits (local + remote)
          git log --oneline --all --graph --decorate
Fetch vs Pull

fetch ≠ pull

fetch met à jour ta connaissance du remote (sans toucher tes fichiers). pull = fetch + merge (ou rebase) → ça modifie ta branche locale.

Fetch / Pull 
git fetch origin

# Voir ce qui a changé (après fetch)
git log --oneline --decorate --grah --all

# Intégrer les changements dans la branche courante
git pull

4) Les bases (init / clone / status)

Créer un dépôt local, ou récupérer un dépôt GitHub proprement.

Initialisation

Créer un dépôt (local)

À faire une seule fois, dans le dossier du projet.

Commandes 
mkdir mon-projet
cd mon-projet
git init
git status

Ensuite tu peux connecter à GitHub (remote) :

Connecter à GitHub 
git remote add origin https://github.com/USER/REPO.git
got remote -v
Clonage

Récupérer un dépôt GitHub (clone)

Le clone crée un dossier local avec tout l’historique + le remote origin déjà configuré.

Commandes 
git clone https://github.com/USER/REPO.git
cd REPO
git remote -v
git status

6) Branches, merge, Pull Requests

Isoler une modification, la relire, puis fusionner proprement (local ou via GitHub).

Concept

Une branche, c’est quoi ?

Une branche est un pointeur vers un commit. Créer une branche, c’est créer un nouveau pointeur pour travailler sans casser main.

  • main : branche “stable”
  • feature/... : nouvelle fonctionnalité
  • fix/... : correctif

Commandes

Workflow “branche → merge” (local)

Workflow 
git checkout -b feature/ma-feature
# ... bosser sur la feature ...
git status
git add .
git commit -m "Ajouter ma feature"

# Revenir sur main
git checkout main
git pull
git merge feature/ma-feature
git push
GitHub

Workflow Pull Request (recommandé)

Au lieu de fusionner direct en local, tu pousses ta branche puis tu ouvres une PR sur GitHub. Ça force une relecture, garde l’historique clair, et évite des merges “sales”.

PR — étapes 
git checkout -b feature/ma-feature
# ... commits ...

git push -u origin feature/ma-feature

7) Conflits : quoi faire (sans paniquer)

Un conflit = Git ne sait pas décider entre deux modifications. Tu choisis, tu valides, tu continues.

Réflexe

La règle d’or

Fetch/Pull avant de commencer une grosse modif. Et commits petits + fréquents.

Avant de travailler 
git pull
git status
Résolution

Résoudre un conflit (merge)

Étapes 
# tu lances un pull ou un merge -> conflit
git status
# éditer les fichiers en conflit, chercher les marqueurs puis : 
git add . 
git commit -m "Résoudre conflit entre main et feature/ma-feature"
git push
